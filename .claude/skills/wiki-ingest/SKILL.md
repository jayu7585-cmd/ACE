# wiki-ingest: 원자료를 위키에 통합하기

이 스킬은 `CLAUDE.md` 4.1절(Ingest)을 실행하는 절차서다. 규약(파일명, frontmatter, 링크, 콜아웃)은 `CLAUDE.md` 3절을 따른다. 이 문서와 CLAUDE.md가 충돌하면 **CLAUDE.md가 우선**한다.

목표는 요약을 하나 더 만드는 것이 아니다. **기존 위키를 새 자료로 갱신하는 것**이다. 자료 1건이 10–15개 페이지를 건드리는 것이 정상이다.

## 0. 인자 해석

`$ARGUMENTS`
- **경로가 있으면** (예: `raw/papers/kahneman1979.pdf`): 그 자료를 처리한다. 여러 개면 순서대로 처리한다.
- **비어 있으면**: `python3 .claude/skills/wiki-ingest/scripts/pending.py`를 실행해 미처리 목록을 보여주고, 무엇을 처리할지 사용자에게 묻는다.
- **`배치` 또는 `알아서`가 포함되면**: 2단계(논의)를 건너뛰고 끝까지 진행한 뒤 마지막에 한꺼번에 보고한다.

## 1. 준비

1. `grep "^## \[" wiki/log.md | tail -5`로 최근 작업 맥락을 확인한다.
2. `wiki/index.md`와 `wiki/overview.md`를 읽는다. 이것이 **현재 위키의 지도**다.
3. 같은 원자료가 이미 처리됐는지 확인한다: `grep -rl "<raw 경로>" wiki/sources/`. 이미 있으면 새로 만들지 말고 "재-ingest(보강)"로 처리할지 사용자에게 묻는다.

## 2. 읽기

형식별로 읽는다. **끝까지** 읽는다. 앞부분만 읽고 요약하지 않는다.

| 형식 | 방법 |
|---|---|
| `.md` / `.txt` | Read. 길면 offset/limit로 나눠 전부 읽기 |
| `.pdf` | `pdftotext -layout 파일 -`로 텍스트 추출(없으면 `pdf` 스킬 사용). 스캔본이면 Read의 `pages`로 이미지 확인 |
| 이미지가 들어 있는 `.md` | 텍스트를 먼저 읽고, 논지에 중요한 그림만 `raw/assets/`에서 따로 열어 본다 |
| `.csv` / `.xlsx` | 구조(변수, 표본 크기, 기간)와 기술통계만 파악한다. 분석이 필요하면 사용자에게 제안한다 |
| 녹취·메모 | 화자, 날짜, 맥락을 먼저 확인한다. 사용자 본인의 메모는 "관점·가설"로 다루고 "연구 증거"와 구분한다 |

읽으면서 추출할 것:
- 서지 정보 (저자, 연도, 게재처, DOI)
- 핵심 주장 3–7개와 각 주장을 뒷받침하는 증거 (연구설계, 표본, 효과크기, 통계 결과)
- 등장하는 개념, 이론, 인물 → 위키에 **이미 있는지 / 없는지** 구분
- 기존 위키 내용과 **일치하는 점 / 확장하는 점 / 충돌하는 점**
- 한계와 재현성 이슈 (저자가 밝힌 한계 + 알려진 논쟁)

## 3. 논의 (배치 모드면 생략)

사용자에게 짧게 보고하고 **멈춰서 답을 기다린다.**

```
📄 <자료 제목> (저자, 연도)
핵심 요지
1. …
2. …
3. …
위키와의 관계: 새 페이지 N개 예정(…), 갱신 M개 예정(…), 상충 K건(…)
확인할 점: 어떤 측면을 강조할까요? 교육 적용으로 연결할 지점이 있나요?
```

사용자의 답(강조점, 해석, 관점)은 source 페이지의 「사용자 관점」 부분에 반영한다.

## 4. source 페이지 작성

- 경로: `wiki/sources/YYYY-제1저자-짧은제목.md` (영문 제목은 하이픈으로 연결)
- `templates/source.md` 구조를 따르고, Obsidian 템플릿 변수(`{{date}}` 등)는 실제 값으로 바꾼다.
- frontmatter 필수 항목: `type: source`, `title`, `aliases`, `tags`, `authors`, `year`, `kind`, `raw`(원자료 경로, 정확히), `created`, `updated`, `status`
- 수치(표본, 효과크기, p값)는 원문 그대로 옮긴다. 확인할 수 없으면 쓰지 않는다.
- 사용자가 논의에서 준 관점은 `> [!note] 사용자 관점`으로 기록한다.

## 5. 전파 (핵심 단계)

2단계에서 추출한 개념·이론·인물·주제마다 다음을 수행한다.

**중복 확인 먼저**: `grep -rli "<용어>\|<영문 용어>" wiki/`와 `index.md`로 동의어·영문 alias까지 확인한다. 같은 대상의 페이지가 이미 있으면 새로 만들지 않는다.

**기존 페이지가 있을 때 → 갱신**
1. 페이지를 **먼저 Read** 한다. 전체를 덮어쓰지 말고 Edit로 필요한 부분만 고친다.
2. 새 증거는 해당 절에 불릿으로 추가하고 끝에 `([[sources/…]])`를 단다.
3. 기존 주장과 충돌하면 기존 문장을 지우지 말고 바로 아래에 추가한다:
   ```
   > [!warning] 상충
   > [[sources/A]]는 X라고 보고하지만, [[sources/B]]는 Y를 보고한다. 차이의 가능한 원인: 표본/측정/맥락 …
   ```
4. frontmatter를 고친다: `updated`는 오늘 날짜로, `sources`는 +1. 근거가 3개 이상 쌓이고 구조가 안정되면 `status`를 `seed` → `growing` → `mature`로 올린다.
5. 사용자가 직접 쓴 흔적(스타일이 다른 문단, 사용자 메모)은 건드리지 않는다.

**페이지가 없을 때 → 생성 판단**
- 새 페이지를 **만든다**: 자료에서 핵심 역할을 하는 개념·이론, 또는 앞으로 다른 자료에서도 나올 가능성이 높은 개념, 주요 저자
- 새 페이지를 **만들지 않는다**: 한 번 스쳐 지나가는 용어. source 페이지 본문에만 언급하고, 3회 이상 여러 자료에서 등장하면 그때 만든다
- 해당 유형의 템플릿(`templates/concept.md` 등)으로 `status: seed` 페이지를 만든다. 빈 섹션은 지우지 말고 `_아직 없음_`으로 둔다.

**연결**
- source 페이지에서 관련 페이지로, 관련 페이지에서 source 페이지로 **양방향 링크**를 건다.
- 여러 개념을 묶는 주제 허브(`wiki/topics/`)가 있으면 그곳에도 새 페이지 링크를 추가한다.
- 교육 현장 적용 아이디어가 뚜렷하면 해당 개념 페이지에 `> [!example] 교육 적용` 콜아웃을 달고, 설계안 수준이면 `wiki/applications/` 페이지를 제안한다(바로 만들지는 않는다).

**근거 규칙**
- 자료에 있는 내용 → 출처 링크를 단 일반 문장
- Claude의 해석·연결·종합 → `> [!note] 종합(LLM)` 콜아웃 안에만 쓴다
- 재현성 논란이 알려진 효과(예: 자아고갈, 일부 점화효과)는 반드시 명시한다

## 6. overview.md 점검

이 자료가 위키의 핵심 논지(Evolving Thesis)를 강화·약화·수정하는지 판단한다. 영향이 있으면 해당 문장을 고치고 출처를 단다. 영향이 없으면 건드리지 않는다.

## 7. index.md 갱신

- 새 페이지를 알맞은 섹션에 추가한다: `- [[페이지명]] — 한 줄 요약 (sources: n, status)`
- 기존 항목의 `sources` 수, `status`, 요약이 바뀌었으면 고친다.
- 섹션의 `_아직 없음_`은 첫 항목을 넣을 때 지운다.
- index의 `updated` 날짜를 오늘로 고친다.

## 8. log.md 기록 (append-only)

**파일 맨 아래에** 추가한다. 기존 항목은 절대 수정하지 않는다.

```
## [YYYY-MM-DD] ingest | 자료 제목
- 원자료: raw/…
- 생성: [[…]], [[…]]
- 갱신: [[…]], [[…]]
- 상충: [[…]] (요지)  ← 없으면 생략
- 열린 질문: …          ← 없으면 생략
```

## 9. 검증

1. `python3 scripts/wiki_lint.py`를 실행한다. 깨진 링크, 고아 페이지, index 미등재, frontmatter 누락이 **이번 작업으로 생긴 것이면 모두 고친다.**
2. `python3 .claude/skills/wiki-ingest/scripts/pending.py`로 처리한 자료가 목록에서 빠졌는지 확인한다(`raw:` 경로 오타를 잡아낸다).
3. 마지막 lint 이후 ingest가 10건 이상이면 보고할 때 `/wiki-lint`를 제안한다(`deep_check.py` 첫 줄에 건수가 나온다).

## 10. 커밋

git 저장소이면 자료 1건마다 커밋한다. 커밋 메시지는 log 제목과 같은 형식을 쓴다:
`ingest | 자료 제목`

## 11. 보고

```
✅ ingest 완료: <자료 제목>
- 생성 (N): [[…]], …
- 갱신 (M): [[…]], …
- 상충 표시: …
- 열린 질문 / 다음에 읽을 만한 자료: …
- lint: 통과
```

배치 모드에서 여러 건을 처리했다면 자료별로 한 줄씩 요약하고, 마지막에 전체 합계와 lint 결과를 보고한다. 배치에서는 10건마다 lint를 한 번 돌린다.

## 하지 말 것

- `raw/`의 파일을 수정·이동·이름 변경·삭제하지 않는다 (원자료는 불변)
- 기존 위키 페이지를 Write로 통째로 덮어쓰지 않는다 (Read → Edit)
- 원문에 없는 수치·인용문을 지어내지 않는다
- 논의 단계에서 사용자의 답을 기다리지 않고 진행하지 않는다 (배치 모드 제외)
- 페이지를 삭제하거나 대규모로 이름을 바꾸지 않는다 (필요하면 제안만)
